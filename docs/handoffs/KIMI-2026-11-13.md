## KM-04 方案摘要

- 旧 `/api/game` 使用六只六属性模板和 `fire_fox_s1` 等专属技能，不能直接承接 `/duel` 的 38 只八卦宠物、品阶/觉醒和 `skill_effects` 代码。
- start 必须接收 `player_pets.id` 实例 ID，再映射 `template_id + level + awakening_level`；`pet_baihu` 是模板 ID，不能当玩家实例 ID。八卦技能不读旧 `equipped_skills`。
- 保留现有 `POST /api/v2/battle/pve/start` 的 `{teamPetIds:[instanceId]}` 形状，新增同前缀 action/state；action 只接收 `{skillCode,actionId}`，服务端负责技能校验、AI、RNG、回合、胜负、同进程重放响应与唯一落库。
- 前端只渲染服务端快照和 events，移除权威链中的本地 `resolveSkill/pickEnemySkill/endTurn/checkOver/reportBattle`；`/duel` 不再误用只返回排行榜字段的 `/pvp/match` 作为 PvE 对手来源。
- 建议共享无副作用 `duel-core.js + .d.ts`，由浏览器和 Node 注入相同 seeds 配置，服务端注入 RNG；不复制两套公式，不要求 Node 直接运行带 alias 的 TS。
- 第一阶段只用内存战斗、不发奖励；跨进程持久化、actionId 唯一约束及迁移另行派工。完整请求/响应、记录字段、测试清单和文件归属见 KIMI REPORT 的 KM-04 节。
