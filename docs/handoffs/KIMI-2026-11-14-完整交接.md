## 5. 核心代码现状（KIMI 自产，已被 Codex 原样合入）

### 5.1 `src/utils/duel-core.js`（约 166 行，无外部 import，Node 可直接加载）

导出签名：

```js
statsOf(tier, level, awaken, config)            // → {maxHp,atk,def,spd}
createFighter(petId, level, awaken, config)     // → DuelFighter | null（petId 是模板 ID）
coefAgainst(attacker, defender, config)         // → 1 | 1.3，支持 'a,b' 与 'all'
resolveSkill(actor, target, skillCode, side, rng, config) // → DuelEvent[]，原地修改 fighter
endTurn(fighter)                                // 冷却-1、增益回合-1，无事件
pickEnemySkill(enemy, rng)                      // → 技能 code
winnerOf(player, enemy)                         // → 'player'|'enemy'|null，不改状态
```

配置形状固定：`{tiers, trigrams, pets, economy, skillEffects}`。
`skillEffects` 是 `docs/seeds/skill_effects.json` 的 **`effects` 数组**，不是整个 JSON 根。
从数据库读 tiers/trigrams 时必须把 `power_coef/skill_slots/opposite` 映射回核心 camelCase；经济参数可复用 `server/utils/economy.js` 的 `readEconomy(db)`（seeds 默认 + 运行期覆盖）。**核心内部不查库、不抽随机、无副作用导入。**

属性公式：`scale = tierCoef * (1 + levelCoef*(level-1)) * (1 + awakenBonus)`；
`maxHp=round(80*scale)`、`atk=round(14*scale)`、`def=round(8*scale)`、`spd=round(10*scale)`。

fighter 字段（必须完整保留，不能只存 HP）：
`petId,name,pinyin,tier,trigram,level,awaken,maxHp,hp,atk,def,spd,shield,atkBuff,buffTurns,skills[{code,name,cost,cd,remain}]`。
技能槽位 = `skillSlots`（默认 2，上限 4），按 `skillEffects` 顺序取前 N；冷却 `damage_aoe=3`、`heal_pct=2`、其余 0。

**路由/会话层必须知道的行为细节（核心不做这些校验）：**

- `resolveSkill` 对未知技能**回退 `skillEffects[0]`**，且不检查技能是否属于 actor、`remain` 是否为 0、战斗是否已结束。路由必须先精确匹配 actor 自己的技能并拒绝冷却/非法/已结束请求；非法请求不得调用核心、不得改冷却、不得消耗 RNG。
- `resolveSkill`/`endTurn` **原地修改** fighter；返回值只是事件数组，不能用返回值替换 fighter。
- 伤害：先抽 1 次闪避（`rng()<0.08` → 只返回 `miss`）；未闪避再抽 1 次暴击（`<0.12`，×1.6）。威力 `damage_aoe=60`、`damage_burn=70`、其余 damage=100。`raw=round(atk*(1+atkBuff)*power/100*coef*(100/(100+target.def))*(crit?1.6:1))`。
- 事件顺序：可选护盾吸收 `shield` → `hit/crit` → 可选 `ko`。治疗 `heal`（25% maxHp）、获得护盾 `shield`（20% maxHp）、增益 `buff`（atkBuff=0.2、buffTurns=2）各只返回一条；`stun` 只产生 0 伤害文案；`first_strike` 兜底为 `round(atk*0.6*(100/(100+def)))` 的 `hit` + 可选 `ko`。
- **`DuelEvent.side` 是行动方，不是目标方**；事件没有 `target` 字段。伤害前的护盾吸收事件 side 也是攻击方，却描述 target 的护盾。页面不能把所有 `shield` 解释为「side 自己获得护盾」。
- **没有 burn/stun 状态字段**：灼烧只有 70% 单次伤害（seeds 文案写 2 回合 DOT，但实现没有），stun 不附加眩晕。不得伪称 DOT/眩晕已实现；补齐需另立行为变更任务。
- `pickEnemySkill`：优先 `remain===0` 的技能，否则全部；再优先 damage/first_strike；抽 1 次 RNG；空池兜底 `'damage_single'`。
- `winnerOf`：先判 `enemy.hp<=0 → 'player'`，再判 `player.hp<=0 → 'enemy'`。

## 6. KM-06 服务端接入契约（全文在 REPORT KM-06 节，此处为不可违反的要点）

1. **action 编排顺序**：认证/归属/actionId 重放检查 → active 与技能校验 → 玩家 `resolveSkill` → `winnerOf` → 未终结才 `pickEnemySkill` + AI `resolveSkill` → `winnerOf` → **先 `session.log.push(...events)` 累计完整日志** → 有胜方则 finished 且 `battle_records` 只写一次（log_json 含终结事件，零奖励）；无胜方才双方 `endTurn` 并 `turn+=1`。玩家获胜后不得执行 AI；任一方终结后不得 endTurn/加 turn。
2. **actionId 重放**：同 battleId+同 actionId+同请求体 → 返回缓存响应，不推进 RNG、不重复写库；同 actionId 不同体 → 409。重放检查必须早于「已结束」拒绝。第一阶段仅同进程内存重放，**不声称跨进程持久幂等**。
3. **内部会话**（不公开）：`{battleId,ownerId,playerPetInstanceId,status,turn,player,enemy,winner,log,rng,recorded,replayByActionId}`。`rng` 是函数、重放缓存是 Map，均不可 JSON 序列化；ownerId/完整 log/落库标记不进公开 fighter。
4. **公开快照**：`{battleId,status,turn,player,enemy,winner,events}`，未结束 `winner=null`。start `events=[]`；action 只放本次新事件；GET state 建议 `events=[]` 且不推进回合/RNG（避免刷新重放旧特效）。如需 `petInstanceId/templateId` 在响应映射时附加，不改核心 ID 语义。
5. **RNG 次数**：伤害先闪避后暴击（闪避则少抽 1 次）；治疗/盾/增益/stun 不抽；AI 选技抽 1 次（玩家已获胜则不调用）。未终结双方伤害技能通常 5 次，但必须按实际分支断言，不能固定假设。非法/冷却/GET/重放/endTurn 零消耗。`Math.random` 闭包不能重启恢复；未来持久化需可序列化 PRNG 状态或固定算法版本后 `seed+drawCount`，不能 stringify 函数、不能恢复时重置 seed 从头抽。
6. **给 Codex 路由复验的最小测试点**：见 REPORT KM-06 第 6 小节（实例/模板 ID 拒绝混用、他人宠物/战斗拒绝、序列 RNG 各分支、GET 无副作用、两种胜方只落一条 8 列记录、终结重放不重复写库、旧 result 仍 501 零奖励）。
