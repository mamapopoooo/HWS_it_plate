# 战斗引擎选型（DSH 建议稿）

> **结论：** Vue + CSS 做战斗外壳，PixiJS 只承担特效层，二期再用 Rive/Spine 做立绘骨骼动画。
> 不选 Phaser / Cocos 的原因：回合制没有物理与实时碰撞需求，引入游戏框架会让
> Vue 状态与引擎场景双份维护，课室设备上包体与内存也吃紧。

## 一、为什么是「外壳 + 特效层」两层

```
┌ 战斗外壳（Vue + CSS）──────────────────────────┐
│ 回合流程、技能按钮、血条、日志、结算 —— 全部是「界面」 │
│ 好处：可访问性（键盘/读屏）、响应式、易改文案与配色     │
└───────────────────────────────────────────────┘
            │ 只在这一处调用
┌ 特效层（可替换）───────────────────────────────┐
│ M1：CSS（水墨爆、震动、飘字）—— 零依赖            │
│ M2：PixiJS 7（已在依赖里）—— 粒子、光效、拖尾      │
│ M3：Rive / Spine —— 立绘呼吸、施法动作            │
└───────────────────────────────────────────────┘
```

**关键约定**：外壳永远不直接操作 canvas；所有特效通过一个 `play(type, side)` 的接口请求，
接口背后换引擎不影响战斗逻辑。这与 00-总纲 §10「内容即数据」同源：**表现层可替换**。

## 二、三层各自的取舍

### 1. 外壳：Vue + CSS（必选）

- 回合制的信息密度高（血量、卦属、冷却、状态、日志），DOM 排版比 canvas 省事得多；
- 键盘可操作、字体可缩放，投影与平板都友好；
- 国风质感（宣纸、卷轴、印章按钮）本来就用 CSS 做，放进 canvas 反而难维护。

### 2. 特效层：先用 CSS，需要时换 PixiJS

| 特效 | CSS 能否胜任 | 建议 |
|---|---|---|
| 命中震动、飘伤害数字 | ✅ 完全够 | CSS |
| 技能光爆、水墨扩散 | ✅ 够用 | CSS |
| 持续粒子（火羽、雷弧） | ⚠️ 数量一多就掉帧 | PixiJS |
| 拖尾、光带、屏幕扭曲 | ❌ 不适合 | PixiJS |

**所以：M1 全用 CSS；等 KIMI 的技能表定稿、确实需要大量粒子时，再把粒子单独搬进 PixiJS。**

### 3. 立绘动画：Rive 或 Spine（二期）

- **Rive**：Web runtime 免费、状态机好做（待机/受击/施法）、文件小，适合「同一张立绘的有限动作」；
- **Spine**：生态成熟、美术熟悉度高，但 runtime 需授权；
- 共同前提：**美术要产出骨骼文件**，现在只有静态图，二期再上。

## 三、不选 Phaser / Cocos 的理由

| 理由 | 说明 |
|---|---|
| 需求不匹配 | 回合制没有物理、碰撞、摄像机、场景切换的需求，框架 90% 的能力用不上 |
| 双份状态 | 引擎有自己的 scene/update 循环，与 Pinia + Vue 响应式要手工同步，容易出「血量显示不同步」的经典 bug |
| 课室性能 | 班级平板/老旧笔记本上，一个 1MB+ 的引擎运行时是实打实的首屏成本 |
| 可维护性 | 学校场景下维护者是教师 + AI，DOM 调试比 canvas 场景树直观得多 |

## 四、如果以后真要上实时对战

届时再引入 PixiJS 做**单场景战斗画布**（不含 UI），Vue 只负责外壳与结算。
不建议那时才换 Phaser——除非要做「走位 + 实时技能」的动作玩法，那是另一个产品了。

## 五、给其他 Agent 的接口约定

```ts
// 外壳 → 特效层（M1 由 CSS 实现，M2 可换成 PixiJS，签名不变）
type FxType = 'hit' | 'crit' | 'miss' | 'heal' | 'shield' | 'buff' | 'cast' | 'switch' | 'ko'
interface BattleFxApi {
  play(type: FxType, side: 'player' | 'enemy', payload?: { value?: number }): Promise<void>
}
```

战斗逻辑（伤害、克制、暴击）在 `src/utils/duel.ts`，**与表现层完全解耦**，KIMI 可以独立替换为服务端权威结算。
