## 3. 身份与认证收口决策

新身份规则：students 是名册权威源；学号保留为字符串与前导零；中文/英文名按已约定空白和大小写归一化后校验，空英文名不得构成匹配。

两个现存入口继续保留，内部调用同一名单认证函数：
- POST /api/auth/student/login：正式前端认证入口。
- POST /api/v2/auth/student/login：兼容入口，语义相同，不再自动接纳名单外学号。
- /api/auth/me 与 /api/v2/auth/me 的公共身份字段对齐；旧字段保留，新增字段追加。

所有入口复用同一事务：查名单、解析现有身份、同步档案、确保 trainer、更新登录时间，再签发 token。不得重置 game_points、宠物、抽卡记录和其他游戏资产。

现有 users.id 保持不变；username=学号为目标。旧数据先出只读盘点方案，不能直接运行迁移：
1. 只有裸学号身份：沿用该 id。
2. 只有 stu_<学号>：记录候选映射，核对身份与引用后规划兼容；不直接建第二条用户。
3. 两者同时存在、教师账号占用裸学号、名单重复或无法唯一关联：阻止自动归并，保留全部数据，出冲突清单。
4. 本阶段不转移或相加资产、不删旧用户、不改主键。需要变更旧数据时单列备份、审计、回滚及用户决定项。

测试必须覆盖“两个入口登录同一人仍只有一条身份”、未知学号即使姓名正确也拒绝、错误姓名拒绝、中英文各自成功、旧 token 的 userId 引用不漂移。

## 4. API 与页面边界

Codex 统一 API_ROOT = BASE_URL + api，业务接口分别接 v2/v3，不回退为写死根路径。
roster 写请求遇 2xx HTML、空响应或错误形状也必须报告失败，不能当成功空对象。处理401与原主分支保持一致。

页面按实际挂载验收：/teacher、/admin/students、/lobby、/student 等现有入口先保留，不以历史文档为由删除 v3 页面。本轮修正文档对现状的表述，统一导航另列后续任务，禁止顺手重做整套页面。

DSH 当前页面调用 roster API 的行为与“页面只调 adapter”规范有差异：保留一个有明确鉴权、响应校验、失败上抛的集中名单客户端，经 adapter 对外导出给页面；不复制第二套请求器、不恢复静默假数据。共享实现由 Codex收口，DSH只迁移调用与验证。

只读演示占位需可识别；认证、导入、编辑、积分同步及战斗写库失败不得用 demo 数据冒充成功。1.5秒前端超时不等于服务端未提交，写操作失败后先刷新核对，不盲目重复提交。

## 5. 名单修复契约

- 返回名册真实 gamePoints 和 loggedIn；虚构已登录且非零积分的学生必须能查出真值。
- import 按“键是否存在”决定更新列；前端按表头映射保留缺席列信息，不能给每行预填所有空字段。
- 新学生缺少必要信息明确报错，不能默默写 grade=0 或无效 class_id。已有学生只改本次出现列。
- 列出现但空白不得隐式清空旧档案：按用户“清空走单条编辑”的口径拒绝或保留并给明确原因；预演与提交共用校验和列决策。
- 预演必须报告将更新/跳过的列、无效/重复学号及新旧记录分类，不包含真实名单的测试快照。
- 单条编辑允许明确清空可选字段；年级按显式有效值或可确定班级/课程推导，不用 || 吞掉0；无法确定就报错或保留旧有效值。
- 转班在同一事务中同步 students 与 users；目标班级年级无法确定时不猜测，不部分提交。
- 迁移使用实际 PRAGMA 检查列/索引；重复学号预检失败即中止，不再吞错。已有 v9/v10 标记的库也须用新的增量修复版本验证约束。版本号由 Codex检查整合分支后预留，不能抢用数字。

## 8. 验收与回滚

临时库回归矩阵：双登录入口/中英文/错学号/姓名回落拒绝/身份冲突；真实积分与登录映射；简表保留档案；空白可选列；重复学号迁移中止及已标记库修复；跨年级转班后再登录；battle记录落库与双方计数；非JSON API不假成功。

独立工作区内执行 node 直跑 vue-tsc、vitest run、vite build、verify-build；涉及数据种子加 _validate，涉及编码加 check-mojibake。报告实际测试数与覆盖内容，不沿用45/207历史数字。

测试库必须与生产及其他工作区隔离。当前 db.js 固定 server/pet-garden.db，禁止直接 import 后在未知库上跑测试；使用独立检出副本内临时库或先设计明确的测试数据库注入方式，测试启动前断言绝对路径在测试目录。

任何一批失败先修本批，不把半成品推进main。代码回退用保留历史的revert方案，不强推；数据库本阶段只做增量，真实数据变更另有备份与恢复演练后才能进入发布评估。
