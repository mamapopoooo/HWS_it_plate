# 集市商品映射核对（DSH · 2026-11-13）

> 目的：Codex 要求「按已存在商品 ID 逐项列与后端 itemId/skinId 的映射，不要把配置商品 id 猜成数据库 id」。
> 结论先行：**两套商品体系没有语义交集，无法建立 1:1 映射**，因此页面禁用成交是正确处置。

## 一、配置侧（`docs/seeds/shop.json`，前端展示用）

| 配置 id | 名称 | 分类 | 展示价（G6） |
|---|---|---|---|
| `item_ticket_single` | 签券 | utility | 5 |
| `item_rename` | 改名符 | utility | 15 |
| `item_title` | 称号 | utility | 49 |
| `item_trigram_reroll` | 换卦符 | utility | 59 |
| `item_battle_refill` | 补卦力 | utility | 3 |
| `item_skin_school` | 校服 | decor | 按皮肤价 |
| `item_skin_hanfu` | 云纹汉服 | decor | 按皮肤价 |
| `item_skin_season` | 节气限定 | decor | 按皮肤价 |
| `item_fragment_box` | 灵纹匣 | items | — |

## 二、后端侧（`GET /api/v2/shop/items`，实测返回 8 条）

| 后端 id | 名称 | type | 价格 |
|---|---|---|---|
| `item_1` | 经验药水（小） | exp | 50 |
| `item_2` | 经验药水（大） | exp | 150 |
| `item_3` | 普通宠物蛋 | gacha | 200 |
| `item_4` | 稀有宠物蛋 | gacha | 500 |
| `item_5`…`item_8` | （其余 v1 商品，同为 `item_N` 编号） | — | — |

`GET /api/v2/shop/skins` → **`{"skins":[]}`**（空）。

## 三、核对结论

| 检查 | 结果 |
|---|---|
| 商品语义是否对应 | ❌ 后端是 v1 的「经验药水 / 宠物蛋」，配置是 v3 的「签券 / 改名符 / 称号 / 换卦符 / 补卦力 / 灵纹匣」 |
| id 是否可推断 | ❌ 后端统一 `item_N` 顺序编号，与配置的语义 id 无任何可推导关系 |
| 皮肤是否可买 | ❌ 后端 skins 为空 |
| 价格是否一致 | ❌ 两套价格体系不同（后端 50/150/200/500，配置 5/15/49/59/3） |

**因此**：`POST /api/v2/shop/buy` 用配置 id 调用必然失败或买错东西；页面本轮**禁用成交**、只展示价目并显式说明「未开通、不扣灵石」。

## 四、要开通成交，需要后端做一件事（二选一）

1. **按 v3 seeds 重建商品表**：把 `docs/seeds/shop.json` 的 9 条写进 `shop_items`，`id` 用配置 id（或提供稳定映射表），价格按 `economy.skin/…` 计算；
2. **提供 v3 商城接口**：`GET /api/v3/shop/items` 返回 `{ id, name, price, limit, category }`，前端直接以服务端返回渲染（配置只作兜底），下单 `POST /api/v3/shop/buy { itemId, qty }`。

在此之前，前端不应存在任何本地扣款路径。
